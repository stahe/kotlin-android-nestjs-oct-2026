    3. Chapitre 2 - Installation du serveur [NestJS]

    Le client [Kotlin] de ce document a besoin d’un serveur à interroger : le serveur [NestJS] de l’application [RdvMedecins], livré avec ce document dans le dossier [rdvmedecins-nestjs-server]. Ce document étant consacré à [Kotlin], ce serveur y est traité comme une « boîte noire » : ce chapitre explique comment l’installer, le configurer, créer sa base de données [MySQL], le lancer et le tester, mais n’en étudie pas le code. Le lecteur qui souhaite apprendre [NestJS] pourra lire le document Introduction au langage TypeScript et au framework NestJS (2026).

    Ce chapitre reprend à l’identique le chapitre 2 du cours Un exemple de client / serveur - Flutter / NestJS (2026) : le serveur, sa base de données et ses tests sont exactement les mêmes. Le lecteur qui a déjà installé ce serveur pour le cours Flutter peut passer directement à la dernière section de ce chapitre, « Lancer le client Kotlin pour la première fois ».

    3.1. Installation de Laragon

    Pour créer la base de données [MySQL] utilisée par le serveur [NestJS], nous allons utiliser l’outil Laragon. En septembre 2026, Laragon est disponible à l’URL [Download Laragon – Fast & Modern Dev Environment ]. Laragon amène avec lui des outils qui permettent d’installer un serveur PHP et le SGBD [MySQL] :

    • en [1], un serveur web Apache ;
    • en [2], le SGBD [MySQL] ;
    • en [3], un outil de messagerie que nous n’utiliserons pas ;
    • en [4], lance tous les services (Apache, [MySQL], MailPit) ;
    • en [5], affiche la page web d’URL [http://localhost]. Par défaut, cette URL désigne le dossier <laragon-install>\www où <laragon-install> est le dossier d’installation de Laragon ;
    • en [6], lance l’Outil HeidiSQL qui permet de gérer des bases de données MySQL. C’est avec cet outil que nous créerons la base de données utilisée par le serveur [RdvMedecins] ;
    • en [7], ouvre un terminal dans lequel tous les binaires utiles à Laragon sont dans le PATH ;
    • en [8], ouvre un explorateur windows dans le dossier associé à l’URL [http://localhost] ;

    3.3. Création de la base de données

    La base de données [dbrdvmedecins] reprend, dans sa structure, celle du document original (2014, Spring 4 / [MySQL] 5) : mêmes tables [medecins], [clients], [creneaux], [rv], mêmes clés étrangères, même contrainte d’unicité. Seule nouveauté, apportée par l’étape « authentification » de ce portage : la table [users]. Les relations entre ces tables sont les suivantes : un médecin ([medecins]) possède plusieurs créneaux horaires ([creneaux], clé étrangère [id_medecin]) ; un rendez-vous ([rv]) associe un jour, un créneau (donc un médecin) et un client ([clients]) ; la table [users] est indépendante des quatre autres : elle ne sert qu’à l’authentification.

    -- =========================================================================
-- Base de données [dbrdvmedecins] - MySQL 8
--
-- Ce script reprend EXACTEMENT le schéma relationnel du document original
-- (2014, Spring 4 / Spring Data / MySQL 5) : mêmes tables, mêmes colonnes,
-- mêmes clés étrangères, même contrainte d'unicité. Seul le moteur de base
-- de données change de nom (MySQL 5 -> MySQL 8), pas la structure.
--
-- La table [users] apparaît maintenant (étape "authentification" de ce
-- portage). Le document original utilisait TROIS tables (users, roles,
-- users_roles) pour permettre à un utilisateur d'avoir PLUSIEURS rôles.
-- Puisque cette application ne connaît que deux rôles mutuellement
-- exclusifs (ADMIN, USER), nous simplifions ici à une seule colonne [role]
-- sur la table [users] plutôt que de reconstruire la relation plusieurs-à-
-- plusieurs d'origine - une simplification pédagogique assumée, documentée
-- dans le chapitre "Authentification" du cours.
-- =========================================================================


CREATE DATABASE IF NOT EXISTS dbrdvmedecins CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
USE dbrdvmedecins;

-- on repart d'une base vide à chaque exécution du script (pratique en développement)
DROP TABLE IF EXISTS rv;
DROP TABLE IF EXISTS creneaux;
DROP TABLE IF EXISTS clients;
DROP TABLE IF EXISTS medecins;
DROP TABLE IF EXISTS users;

-- -------------------------------------------------------------------------
-- table [medecins] : les médecins du cabinet
-- -------------------------------------------------------------------------
CREATE TABLE medecins (
  id      INT AUTO_INCREMENT PRIMARY KEY,      -- clé primaire (identifiant technique)
  version INT NOT NULL DEFAULT 0,               -- n° de version de la ligne (verrou optimiste)
  titre   VARCHAR(5)  NOT NULL,                 -- Melle, Mme, Mr
  nom     VARCHAR(20) NOT NULL,
  prenom  VARCHAR(20) NOT NULL
);

-- -------------------------------------------------------------------------
-- table [clients] : les patients des médecins
-- -------------------------------------------------------------------------
CREATE TABLE clients (
  id      INT AUTO_INCREMENT PRIMARY KEY,
  version INT NOT NULL DEFAULT 0,
  titre   VARCHAR(5)  NOT NULL,
  nom     VARCHAR(20) NOT NULL,
  prenom  VARCHAR(20) NOT NULL
);

-- -------------------------------------------------------------------------
-- table [creneaux] : les créneaux horaires de chaque médecin
-- -------------------------------------------------------------------------
CREATE TABLE creneaux (
  id         INT AUTO_INCREMENT PRIMARY KEY,
  version    INT NOT NULL DEFAULT 0,
  id_medecin INT NOT NULL,                      -- clé étrangère -> medecins(id)
  hdebut     INT NOT NULL,                       -- heure de début du créneau
  mdebut     INT NOT NULL,                       -- minute de début du créneau
  hfin       INT NOT NULL,                       -- heure de fin du créneau
  mfin       INT NOT NULL,                       -- minute de fin du créneau
  CONSTRAINT fk_creneaux_medecin FOREIGN KEY (id_medecin) REFERENCES medecins(id)
);

-- -------------------------------------------------------------------------
-- table [rv] : les rendez-vous pris par les clients
-- -------------------------------------------------------------------------
CREATE TABLE rv (
  id         INT AUTO_INCREMENT PRIMARY KEY,
  version    INT NOT NULL DEFAULT 0,
  jour       DATE NOT NULL,                      -- jour du rendez-vous
  id_creneau INT NOT NULL,                        -- clé étrangère -> creneaux(id)
  id_client  INT NOT NULL,                        -- clé étrangère -> clients(id)
  CONSTRAINT fk_rv_creneau FOREIGN KEY (id_creneau) REFERENCES creneaux(id),
  CONSTRAINT fk_rv_client  FOREIGN KEY (id_client)  REFERENCES clients(id),
  -- un même créneau, un même jour, ne peut être réservé qu'une seule fois
  CONSTRAINT unq1_rv UNIQUE (jour, id_creneau)
);

-- -------------------------------------------------------------------------
-- table [users] : les utilisateurs autorisés à se connecter à l'application
-- -------------------------------------------------------------------------
CREATE TABLE users (
  id       INT AUTO_INCREMENT PRIMARY KEY,
  version  INT NOT NULL DEFAULT 0,
  login    VARCHAR(30) NOT NULL UNIQUE,          -- identifiant de connexion
  password VARCHAR(100) NOT NULL,                -- mot de passe HACHÉ (bcrypt) - jamais en clair
  nom      VARCHAR(40) NOT NULL,                 -- nom affiché une fois connecté
  role     VARCHAR(10) NOT NULL                  -- 'ADMIN' ou 'USER'
);

    Commentons ce code :

    • lignes 20-21 : [CREATE DATABASE IF NOT EXISTS dbrdvmedecins …] puis [USE dbrdvmedecins] — crée la base si elle n’existe pas encore (jeu de caractères [utf8mb4], qui accepte tous les caractères Unicode, accents compris), puis la sélectionne : toutes les instructions qui suivent s’appliquent à elle. Ces deux lignes doivent impérativement venir EN PREMIER : exécutées après les [DROP TABLE …], celles-ci échoueraient faute de base sélectionnée (erreur [No database selected]) ;
    • lignes 24-28 : [DROP TABLE IF EXISTS …] — le script repart d’une base vide à chaque exécution, dans l’ordre inverse des dépendances (rv d’abord, qui référence [creneaux] et clients, jusqu’à users, qui n’est référencée par personne) : [MySQL] refuserait de supprimer une table encore référencée par une clé étrangère ;
    • ligne 58 : [id_medecin INT NOT NULL] puis ligne 63 : [CONSTRAINT fk_creneaux_medecin FOREIGN KEY …] — un créneau appartient toujours à un médecin ;
    • ligne 78 : [CONSTRAINT unq1_rv UNIQUE (jour, id_creneau)] — la règle de gestion centrale de l’application : un même créneau, un même jour, ne peut être réservé qu’une seule fois. C’est cette contrainte, et elle seule, qui empêche un double rendez-vous - ni le contrôleur ni la couche métier ne la revérifient explicitement ;
    • lignes 84-91 : [CREATE TABLE users (…)] — la table ajoutée par cette étape. login est UNIQUE (deux utilisateurs ne peuvent pas partager le même identifiant de connexion) ; password stocke un mot de passe haché par bcrypt (jamais en clair) ; role vaut 'ADMIN' ou 'USER' - une simple colonne texte, là où le document original utilisait trois tables (users, roles, users_roles) pour autoriser plusieurs rôles par utilisateur. Cette application n’ayant besoin que de deux rôles mutuellement exclusifs, la relation plusieurs-à-plusieurs d’origine serait allée au-delà du nécessaire ;
    • lignes 129-131 : [INSERT INTO users …] — deux comptes de démonstration, admin/admin (rôle ADMIN) et user/user (rôle USER), avec leurs mots de passe déjà hachés par bcrypt (10 tours de salage) - jamais en clair, y compris dans ce script de démonstration.

    3.3.2. Exécution du script avec HeidiSQL

    Pour créer la base de données [MySQL] nécessaire au serveur [NestJS], nous procédons de la façon suivante :

    • En [1], vous pouvez sélectionner divers SGBD. La valeur par défaut proposée est le SGBD MySQL. Cela convient ;
    • en [2], vous ouvrez une session de HeidiSQL ;
    • En [1-2], exécutez un fichier SQL puis choisissez le fichier [dbrdvmedecins.sql] que vous trouverez dans le dossier [rdvmedecins-nestjs-server/database] :

    L’exécution du fichier [3] va créer la base [dbrdvmedecins] utilisée par le serveur [NestJS]. Pour le voir, faites F5 dans HeidiSQL pour rafraîchir l’affichage :

    La base de données [dbrdvmedecins] a été créée. On peut en voir le contenu :

    • en [1-3], la table [clients] ;
      • [id] est la clé primaire de la table ;
      • [version] est le numéro de version de la ligne. Ce numéro augmente à chaque modification de la ligne ;
      • [titre, nom, prenom] identifient la personne ;

    • en [1-3], la table [medecins] ;
      • [id] est la clé primaire de la table ;
      • [version] est le numéro de version de la ligne ;
      • [titre, nom, prenom] identifient la personne ;

    • en [1-3], la table des créneaux horaires de consultation des médecins :
      • [id] : clé primaire ;
      • [version] : numéro de version de la ligne ;
      • [id-medecin] : clé étrangère ciblée sur la clé primaire du médecin ;
      • [hdebut, mdebut] : heure et minutes de début de la consultation. Ainsi [8,20] signifie 8h20.
      • [hfin, mfin] : heure et minutes de fin de la consultation.

    • En [1-3], la table [rv] des rendez-vous pris ;
      • [id] : clé primaire ;
      • [version] : numéro de version ;
      • [jour] : jour du rendez-vous ;
      • [id_creneau] : clé étrangère vers la clé primaire du créneau horaire du rendez-vous. Comme un créneau horaire est lié à un médecin, on sait quel médecin assure ce rendez-vous ;
      • [id_client] : clé étrangère vers le numéro (clé primaire) du client qui consulte ;

    • en [1-3], la table [users] qui liste les utilisateurs autorisés à utiliser l’application [NestJS] ;
      • [id, version] : clé primaire, numéro de version ;
      • [login, password] : identifiants de l’utilisateur ;
      • [nom] : nom donné à l’utilisateur ;
      • [role] : son rôle. [ADMIN] a tous les droits. [USER] n’a que des droits de lecture. Il pourra consulter l’agenda d’un médecin mais pas prendre / annuler un rendez-vous ;

    Ces routes constituent l’API JSON que le client [Kotlin] consommera au chapitre 4. [POST /login] est la seule route publique : elle renvoie un jeton JWT que toutes les autres routes exigent dans l’entête [Authorization: Bearer <jeton>]. Les routes de consultation ([GET …]) sont accessibles aux rôles ADMIN et USER ; les deux routes qui modifient des données, [POST /ajouterRv] et [POST /supprimerRv], sont réservées au rôle ADMIN. Les réponses métier sont enveloppées dans un objet [{ status, data }] où [status] vaut 0 en cas de succès.

    3.5. Tester le serveur avec un navigateur

    Depuis l’ajout de l’authentification, toutes les routes de [RdvMedecinsController] exigent un jeton JWT valide : un navigateur, seul, ne permet donc plus de les tester directement. Par exemple :

    http://localhost:8080/getAllMedecins

    C’est le comportement attendu : cette réponse confirme que le serveur protège bien ses routes. Postman (section suivante) est nécessaire pour obtenir un jeton, puis pour l’utiliser.

    3.7. Lancer le client Kotlin pour la première fois

    Le serveur [NestJS] étant démarré, ouvrir le projet [rdvmedecins-kotlin-client] dans Android Studio (cf. chapitre 1) et démarrer l’émulateur. Dans la barre d’outils d’Android Studio, la liste déroulante des appareils doit afficher l’émulateur (par exemple [Pixel 8 API 37]) ; le bouton [Run] (le triangle vert), à côté, compile l’application, l’installe dans l’émulateur et la lance.

    Sans Android Studio, les mêmes étapes s’écrivent en ligne de commande : la tâche Gradle [installDebug] compile et installe l’application, puis [adb] la lance :

    • [installDebug] : construit l’application (comme [assembleDebug], cf. chapitre 1), puis l’installe sur l’appareil connecté - émulateur ou téléphone ;
    • [adb shell am start -n <application>/<activité>] : demande au gestionnaire d’activités d’Android ([am], Activity Manager) de lancer l’activité [MainActivity] de l’application [fr.rdvmedecins.client] - ce que fait le système quand on touche l’icône de l’application.

    L’écran de connexion s’affiche en premier, comme pour les clients précédents de ce cours : deux comptes de démonstration sont fournis avec la base de données du serveur, [admin]/[admin] (rôle [ADMIN], accès complet) et [user]/[user] (rôle [USER], lecture seule). Les boutons « FR »/« EN », en haut à droite, basculent l’interface en anglais, y compris avant toute connexion.

    Le champ « URL du serveur » contient par défaut [http://10.0.2.2:8080] : dans l’émulateur, l’adresse spéciale [10.0.2.2] désigne l’ordinateur qui exécute l’émulateur, donc le serveur [NestJS]. Si la connexion échoue après une dizaine de secondes (message « Login ou mot de passe incorrect. »), c’est le plus souvent que cette adresse ne répond pas : c’est arrivé sur le poste qui a servi à écrire ce document. La solution est décrite au chapitre 5 : la commande [adb reverse tcp:8080 tcp:8080], puis l’URL [http://localhost:8080].
