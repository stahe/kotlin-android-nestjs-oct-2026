    5. Chapitre 4 - Le client Kotlin de l’application RdvMedecins

    5.1. Rappel de l’architecture

    Ce client dialogue avec le serveur [rdvmedecins-nestjs-server] du cours, strictement inchangé, par les mêmes routes HTTP (POST [/login], GET [/getAllMedecins], GET [/getAllClients], GET [/getAgendaMedecinJour/:idMedecin/:jour], POST [/ajouterRv], POST [/supprimerRv]), avec la même enveloppe JSON [{ status, data }] et la même authentification par jeton [JWT] (entête [Authorization: Bearer <jeton>]).

    • ligne 14 : [android.permission.INTERNET] - sans cette permission, toute connexion au serveur échoue. C’est une permission « normale » : elle est accordée à l’installation, sans demande à l’utilisateur ;

    // =========================================================================
// RdvMedecinsApplication.kt
// -------------------------------------------------------------------------
// Première moitié du lib/main.dart de la version Flutter : la construction,
// UNE SEULE FOIS, des services de l'application.
//
// Pourquoi une classe Application ? Sur Android, l'écran (l'Activity, cf.
// MainActivity) est DÉTRUIT puis RECRÉÉ à chaque rotation du téléphone, à
// chaque changement de langue du système, etc. Des services construits
// dans l'Activity seraient donc reconstruits à chaque rotation. L'objet
// Application, lui, est créé au lancement du processus et vit aussi
// longtemps que lui : c'est le bon endroit pour des objets qui doivent
// durer toute la vie de l'application. Il est déclaré dans
// AndroidManifest.xml (attribut android:name de la balise <application>).
//
// L'ORDRE des constructions compte, comme dans la version Flutter :
// AuthService a besoin de SettingsService (l'URL du serveur) ; le client
// HTTP authentifié a besoin d'AuthService (le jeton) ; RdvService a
// besoin du client HTTP authentifié et de SettingsService.
// =========================================================================

package fr.rdvmedecins.client

import android.app.Application
import android.content.Context
import fr.rdvmedecins.client.core.http.AuthInterceptor
import fr.rdvmedecins.client.core.i18n.TranslationsService
import fr.rdvmedecins.client.core.services.AuthService
import fr.rdvmedecins.client.core.services.RdvService
import fr.rdvmedecins.client.core.services.SettingsService
import okhttp3.OkHttpClient
import java.util.concurrent.TimeUnit

class RdvMedecinsApplication : Application() {

    // lateinit : ces propriétés non nulles seront initialisées dans
    // onCreate(), et non dans le constructeur (cf. le cours Kotlin)
    lateinit var settings: SettingsService
        private set
    lateinit var auth: AuthService
        private set
    lateinit var rdv: RdvService
        private set
    lateinit var translations: TranslationsService
        private set

    // appelée par Android au lancement de l'application, avant tout écran
    override fun onCreate() {
        super.onCreate()

        // les préférences de l'application : un petit fichier clé/valeur
        // privé, qui survit à l'arrêt de l'application - l'équivalent du
        // localStorage d'un navigateur
        val prefs = getSharedPreferences("rdvmedecins", Context.MODE_PRIVATE)

        // 1. SettingsService en premier : les autres en ont besoin
        settings = SettingsService(prefs)

        // 2. un client HTTP OkHttp "simple", utilisé par AuthService pour
        //    POST /login. Délais courts : sur mobile, mieux vaut un message
        //    d'erreur rapide qu'une attente interminable si le serveur est
        //    injoignable (mauvaise URL, Wi-Fi coupé...).
        val httpSimple = OkHttpClient.Builder()
            .connectTimeout(10, TimeUnit.SECONDS)
            .readTimeout(15, TimeUnit.SECONDS)
            .build()
        auth = AuthService(settings, prefs, httpSimple)

        // 3. le client HTTP authentifié : une COPIE du précédent
        //    (newBuilder() réutilise sa configuration et ses connexions),
        //    complétée de l'intercepteur qui ajoute le jeton JWT
        val httpAuthentifie = httpSimple.newBuilder()
            .addInterceptor(AuthInterceptor(auth))
            .build()
        rdv = RdvService(httpAuthentifie, settings)

        // 4. les traductions : aucune dépendance envers les autres services
        translations = TranslationsService(assets, prefs)
    }
}

    Commentons ce code :

// AppViewModel.kt
// -------------------------------------------------------------------------
// L'ÉTAT et la LOGIQUE de l'écran principal : la partie "_AppRootState"
// du lib/app.dart de la version Flutter (médecins, patients, agenda
// affiché, erreur, dernière recherche...) et les réactions aux actions de
// l'utilisateur (rechercher un agenda, réserver, annuler).
//
// Pourquoi un ViewModel, plutôt que des états locaux dans la fonction
// @Composable AppRoot (cf. App.kt) ? Parce que l'Activity est détruite et
// recréée à chaque rotation de l'écran (cf. RdvMedecinsApplication) : un
// état local serait perdu - l'agenda affiché disparaîtrait au moindre
// basculement du téléphone. Un ViewModel (bibliothèque Android Jetpack
// "lifecycle") SURVIT à ces recréations : Android le conserve, et le
// redonne à la nouvelle Activity. Il n'est détruit que lorsque l'écran
// est quitté pour de bon. Flutter n'a pas ce problème : la rotation n'y
// détruit rien, seule la taille de l'écran change.
//
// Le découpage obtenu est classique sur Android : App.kt AFFICHE, ce
// ViewModel DÉCIDE et appelle les services.
// =========================================================================

package fr.rdvmedecins.client

import android.util.Log
import androidx.compose.runtime.getValue
import androidx.compose.runtime.mutableStateOf
import androidx.compose.runtime.setValue
import androidx.compose.runtime.snapshotFlow
import androidx.lifecycle.ViewModel
import androidx.lifecycle.viewModelScope
import fr.rdvmedecins.client.core.models.AgendaMedecinJour
import fr.rdvmedecins.client.core.models.Client
import fr.rdvmedecins.client.core.models.CreneauJson
import fr.rdvmedecins.client.core.models.Medecin
import fr.rdvmedecins.client.core.models.RvJson
import fr.rdvmedecins.client.core.services.AuthService
import fr.rdvmedecins.client.core.services.RdvService
import kotlinx.coroutines.CancellationException
import kotlinx.coroutines.launch

class AppViewModel(
    private val auth: AuthService,
    private val rdv: RdvService,
) : ViewModel() {

    // --- état affiché par App.kt (lecture publique, écriture privée) ------
    var medecins by mutableStateOf<List<Medecin>>(emptyList())
        private set
    var clients by mutableStateOf<List<Client>>(emptyList())
        private set
    var agenda by mutableStateOf<AgendaMedecinJour?>(null)
        private set
    var erreur by mutableStateOf<String?>(null)
        private set

    // le créneau en cours de réservation : non null = la boîte de dialogue
    // de réservation est ouverte (cf. App.kt et BookingDialog.kt)
    var creneauEnReservation by mutableStateOf<CreneauJson?>(null)
        private set

    // la dernière recherche (médecin + jour), pour rafraîchir l'agenda après
    // une réservation ou une annulation. Jamais affichée : de simples
    // propriétés suffisent, inutile d'en faire des états Compose.
    private var dernierIdMedecin: Int? = null
    private var dernierJour: String? = null

    init {
        // snapshotFlow { ... } transforme la lecture d'un état Compose en un
        // FLUX de valeurs : il émet la valeur courante de auth.estConnecte
        // tout de suite, puis chaque nouvelle valeur. C'est l'équivalent
        // exact du "watch(() => auth.estConnecte, ..., { immediate: true })"
        // de Vue.js - et de l'abonnement addListener(...) + appel initial
        // que la version Flutter devait écrire à la main.
        // viewModelScope : les coroutines lancées dans cette portée sont
        // automatiquement annulées quand le ViewModel est détruit (plus
        // besoin du removeListener(...) de dispose() côté Flutter).
        viewModelScope.launch {
            snapshotFlow { auth.estConnecte }.collect { connecte ->
                if (connecte) {
                    chargerListesInitiales()
                } else {
                    reinitialiser()
                }
            }
        }
    }

    // -----------------------------------------------------------------------
    // à la connexion (ou à la restauration d'une session mémorisée) : on
    // charge une bonne fois pour toutes les médecins et les patients. Deux
    // coroutines distinctes : les deux requêtes partent EN PARALLÈLE.
    // -----------------------------------------------------------------------
    private fun chargerListesInitiales() {
        lancer { medecins = rdv.getAllMedecins() }
        lancer { clients = rdv.getAllClients() }
    }

    // -----------------------------------------------------------------------
    // à la déconnexion (bouton, ou jeton refusé par le serveur) : on purge
    // l'état métier, pour qu'un nouvel utilisateur ne voie pas, même un
    // instant, l'agenda du précédent
    // -----------------------------------------------------------------------
    private fun reinitialiser() {
        medecins = emptyList()
        clients = emptyList()
        agenda = null
        erreur = null
        creneauEnReservation = null
        dernierIdMedecin = null
        dernierJour = null
    }

    // bouton "Se déconnecter" : il suffit de déconnecter AuthService -
    // snapshotFlow (cf. init) déclenche ensuite reinitialiser()
    fun deconnecter() {
        auth.seDeconnecter()
    }

    // -----------------------------------------------------------------------
    // bouton "Voir l'agenda" de DoctorDayPicker
    // -----------------------------------------------------------------------
    fun rechercherAgenda(idMedecin: Int, jour: String) {
        erreur = null
        dernierIdMedecin = idMedecin
        dernierJour = jour
        chargerAgenda()
    }

    // -----------------------------------------------------------------------
    // bouton "Réserver" d'AgendaView : on se contente d'OUVRIR la boîte de
    // dialogue, en mémorisant le créneau concerné. Avec Compose, une boîte
    // de dialogue fait partie de l'affichage comme le reste : elle est
    // affichée tant que creneauEnReservation n'est pas null (cf. App.kt) -
    // le même principe que la prop "ouvert" du BookingDialog.vue de la
    // variante Vue.js, à l'opposé du showDialog(...) de Flutter.
    // -----------------------------------------------------------------------
    fun demanderReservation(creneau: CreneauJson) {
        creneauEnReservation = creneau
    }

    // bouton "Annuler" (ou appui en dehors) de la boîte de dialogue
    fun fermerReservation() {
        creneauEnReservation = null
    }

    // bouton "Confirmer" de la boîte de dialogue
    fun confirmerReservation(idClient: Int) {
        val creneau = creneauEnReservation ?: return
        val jour = dernierJour ?: return
        creneauEnReservation = null // ferme la boîte de dialogue
        lancer {
            rdv.ajouterRv(jour, idClient, creneau.id)
            chargerAgenda() // le créneau apparaît maintenant occupé
        }
    }

    // -----------------------------------------------------------------------
    // bouton "Annuler" d'un créneau occupé, dans AgendaView
    // -----------------------------------------------------------------------
    fun annulerRv(rv: RvJson) {
        lancer {
            rdv.supprimerRv(rv.id)
            chargerAgenda() // le créneau redevient libre
        }
    }

    private fun chargerAgenda() {
        val idMedecin = dernierIdMedecin ?: return
        val jour = dernierJour ?: return
        lancer { agenda = rdv.getAgendaMedecinJour(idMedecin, jour) }
    }

    // -----------------------------------------------------------------------
    // lance [action] dans une coroutine du ViewModel, et transforme toute
    // exception en message d'erreur affiché à l'écran. Factoriser ce
    // try/catch évite de le répéter dans chaque méthode ci-dessus.
    // Une CancellationException n'est PAS une erreur : c'est le signal
    // d'annulation d'une coroutine (ViewModel détruit), qu'il faut laisser
    // se propager.
    // -----------------------------------------------------------------------
    private fun lancer(action: suspend () -> Unit) {
        viewModelScope.launch {
            try {
                action()
            } catch (e: CancellationException) {
                throw e
            } catch (e: Exception) {
                Log.w("RdvMedecins", "échec d'un appel au serveur", e) // cf. Logcat
                erreur = e.message ?: e.toString()
            }
        }
    }
}

    • lignes 65-66 : la dernière recherche (médecin et jour), pour rafraîchir l’agenda après une réservation ou une annulation. De simples propriétés privées : elles ne sont jamais affichées ;

//   1. on lit l'enveloppe comme un arbre JSON générique (JsonObject) ;

package fr.rdvmedecins.client.core.models

import kotlinx.serialization.DeserializationStrategy
import kotlinx.serialization.json.Json
import kotlinx.serialization.json.JsonNull
import kotlinx.serialization.json.int
import kotlinx.serialization.json.jsonObject
import kotlinx.serialization.json.jsonPrimitive

// la configuration JSON partagée par tout le client :
// - ignoreUnknownKeys : le serveur envoie des champs que ce client
//   n'utilise pas (ex : "version" d'un médecin) - on les ignore plutôt que
//   de lever une exception ;
// - explicitNulls = false : à l'encodage, une propriété null n'est pas
//   écrite (sans effet sur les classes de ce client, mais plus proche du
//   comportement de JSON.stringify côté JavaScript).
val JsonRdv = Json {
    ignoreUnknownKeys = true
    explicitNulls = false
}

// exception levée quand le serveur répond avec un statut métier différent
// de 0 (ressource introuvable, date invalide, erreur serveur)
class ReponseException(val status: Int) :
    Exception("Le serveur a répondu avec le statut d'erreur $status")

// décode le corps d'une réponse {status, data} et renvoie "data" dans le
// type T décrit par [deserialiseur] (ex : Medecin.serializer(), ou
// ListSerializer(Medecin.serializer()) pour une liste de médecins)
fun <T> decoderReponse(corps: String, deserialiseur: DeserializationStrategy<T>): T {
    // 1. l'enveloppe, sous forme d'arbre JSON générique
    val enveloppe = JsonRdv.parseToJsonElement(corps).jsonObject
    // 2. le statut métier
    val status = enveloppe.getValue("status").jsonPrimitive.int
    if (status != 0) {
        throw ReponseException(status)
    }
    // 3. "data", décodé seulement maintenant, dans le type attendu
    val data = enveloppe["data"] ?: JsonNull
    return JsonRdv.decodeFromJsonElement(deserialiseur, data)
}

    Commentons ce code :

    • lignes 36-38 : [JsonRdv] - la configuration JSON partagée par tout le client. [ignoreUnknownKeys = true] : le serveur envoie des champs que le client n’utilise pas ([version] d’un médecin, par exemple) ; sans ce réglage, kotlinx.serialization lèverait une exception à la première clé inconnue ;
    • ligne 43 : [ReponseException] - l’exception levée quand le serveur répond avec un statut métier différent de 0 ;
    • ligne 49 : [decoderReponse(corps, deserialiseur)] - une fonction générique : le paramètre [deserialiseur] (par exemple [Medecin.serializer()], généré par le plugin) indique dans quel type [T] décoder [data] ;
    • lignes 51-59 : le décodage se fait en DEUX temps. D’abord l’enveloppe, lue comme un arbre JSON générique ([JsonObject]) ; puis, seulement si [status] vaut 0, [data] est décodé dans le type attendu. Raison : en cas d’erreur, le serveur place dans [data] une liste de messages là où, en cas de succès, on attend par exemple un agenda. Décoder d’emblée l’enveloppe complète dans le type de succès échouerait sur une réponse d’erreur, avant même d’avoir pu lire le statut.

        // écrit sur le disque en arrière-plan, sans bloquer l'interface.

package fr.rdvmedecins.client.core.services

import android.content.SharedPreferences
import androidx.compose.runtime.getValue
import androidx.compose.runtime.mutableStateOf
import androidx.compose.runtime.setValue
import androidx.core.content.edit
import fr.rdvmedecins.client.core.models.JsonRdv
import fr.rdvmedecins.client.core.models.LoginDemande
import fr.rdvmedecins.client.core.models.LoginResultat
import fr.rdvmedecins.client.core.models.Role
import fr.rdvmedecins.client.core.models.decoderReponse
import kotlinx.coroutines.Dispatchers
import kotlinx.coroutines.withContext
import okhttp3.MediaType.Companion.toMediaType
import okhttp3.OkHttpClient
import okhttp3.Request
import okhttp3.RequestBody.Companion.toRequestBody
import java.io.IOException

class AuthService(
    private val settings: SettingsService,
    private val prefs: SharedPreferences,
    // un client HTTP SANS l'intercepteur d'authentification : POST /login
    // est la seule route publique du serveur, il n'y a pas de jeton à
    // envoyer (cf. RdvMedecinsApplication)
    private val http: OkHttpClient,
) {
    // --- état de la session, observé par l'interface ---------------------
    var estConnecte by mutableStateOf(false)
        private set
    var login by mutableStateOf<String?>(null)
        private set
    var nom by mutableStateOf<String?>(null)
        private set
    var role by mutableStateOf<Role?>(null)
        private set

    // le jeton n'est jamais AFFICHÉ : inutile d'en faire un état Compose.
    // Il est en revanche lu par AuthInterceptor sur un thread réseau :
    // @Volatile garantit que ce thread voit toujours la dernière valeur
    // écrite par le thread principal.
    @Volatile
    var accessToken: String? = null
        private set

    // propriété calculée : relit role à chaque accès (et, lue pendant un
    // affichage, abonne l'affichage aux changements de role)
    val estAdmin: Boolean
        get() = role == Role.ADMIN

    init {
        restaurerSession()
    }

    // -----------------------------------------------------------------------
    // relit une éventuelle session mémorisée lors d'un précédent lancement
    // -----------------------------------------------------------------------
    private fun restaurerSession() {
        val brut = prefs.getString(CLE_SESSION, null) ?: return // pas de session mémorisée
        try {
            // la session a été mémorisée sous forme d'un LoginResultat
            // sérialisé en JSON (cf. seConnecter) : on le relit tel quel
            appliquerSession(JsonRdv.decodeFromString(LoginResultat.serializer(), brut))
        } catch (e: Exception) {
            // contenu illisible (ex : format d'une ancienne version de
            // l'application) : on l'oublie, l'utilisateur se reconnectera
            prefs.edit { remove(CLE_SESSION) }
        }
    }

    // -----------------------------------------------------------------------
    // POST /login. "suspend" : cette fonction peut se mettre en pause le
    // temps que le serveur réponde, SANS bloquer le thread qui l'appelle -
    // l'équivalent d'une fonction async renvoyant un Future<LoginResultat>
    // côté Dart. Elle lève une exception si la connexion échoue.
    // -----------------------------------------------------------------------
    suspend fun seConnecter(login: String, password: String): LoginResultat {
        // withContext(Dispatchers.IO) : le bloc s'exécute sur un thread
        // réservé aux entrées/sorties. Android INTERDIT tout accès réseau
        // depuis le thread principal (NetworkOnMainThreadException) : c'est
        // lui qui dessine l'interface, il ne doit jamais attendre.
        val resultat = withContext(Dispatchers.IO) {
            val corps = JsonRdv.encodeToString(LoginDemande.serializer(), LoginDemande(login, password))
            val requete = Request.Builder()
                .url("${settings.apiBaseUrl}/login")
                .post(corps.toRequestBody(TYPE_JSON))
                .build()
            // execute() : appel BLOQUANT - sans danger ici, on est sur un
            // thread d'entrées/sorties. use { } ferme la réponse à la fin du
            // bloc, quoi qu'il arrive (l'équivalent du try-with-resources de
            // Java, cf. le cours Kotlin).
            http.newCall(requete).execute().use { reponse ->
                // mauvais identifiants : le serveur répond 401 Unauthorized
                if (!reponse.isSuccessful) {
                    throw IOException("Échec de connexion (HTTP ${reponse.code})")
                }
                decoderReponse(reponse.body!!.string(), LoginResultat.serializer())
            }
        }
        // de retour sur le thread de l'appelant (le thread principal) :
        // c'est ici, et non sur le thread d'entrées/sorties, qu'on modifie
        // l'état observé par l'interface
        appliquerSession(resultat)
        prefs.edit { putString(CLE_SESSION, JsonRdv.encodeToString(LoginResultat.serializer(), resultat)) }
        return resultat
    }

    // -----------------------------------------------------------------------
    // déconnexion : on oublie la session, en mémoire et dans les préférences.
    // Doit être appelée sur le thread principal (cf. AuthInterceptor).
    // -----------------------------------------------------------------------
    fun seDeconnecter() {
        accessToken = null
        login = null
        nom = null
        role = null
        estConnecte = false
        prefs.edit { remove(CLE_SESSION) }
    }

    private fun appliquerSession(session: LoginResultat) {
        accessToken = session.accessToken
        login = session.login
        nom = session.nom
        role = session.role
        estConnecte = true
    }

    companion object {
        private const val CLE_SESSION = "rdvmedecins.session"
        private val TYPE_JSON = "application/json; charset=utf-8".toMediaType()
    }
}

La session est mémorisée sous la forme d’un [LoginResultat] sérialisé en JSON, relu avec [decodeFromString(LoginResultat.serializer(), brut)] ;

import okhttp3.OkHttpClient
import okhttp3.Request
import okhttp3.RequestBody.Companion.toRequestBody

class RdvService(
    private val http: OkHttpClient,
    private val settings: SettingsService,

    // -----------------------------------------------------------------------
    // les routes GET
    // -----------------------------------------------------------------------
    suspend fun getAllMedecins(): List<Medecin> =
        appeler(requeteGet("/getAllMedecins"), ListSerializer(Medecin.serializer()))

    suspend fun getAllClients(): List<Client> =

// Portage de lib/core/http/auth_http_client.dart. Deux responsabilités,

//   1. ajouter l'entête "Authorization: Bearer <jeton>" à chaque requête ;

//      (jeton expiré ou invalide).
//
// La version Flutter enveloppait le client HTTP dans une classe à elle,
// faute de mécanisme d'interception dans le package http. OkHttp, lui,
// propose des INTERCEPTEURS : des objets par lesquels passe chaque
// requête avant son envoi, et chaque réponse avant son retour à

package fr.rdvmedecins.client.core.http

import android.os.Handler
import android.os.Looper
import fr.rdvmedecins.client.core.services.AuthService
import okhttp3.Interceptor
import okhttp3.Response

class AuthInterceptor(private val auth: AuthService) : Interceptor {

    // un Handler associé au thread principal : il permet de lui confier du
    // travail depuis un autre thread (cf. intercept ci-dessous)
    private val threadPrincipal = Handler(Looper.getMainLooper())

    // appelée par OkHttp pour CHAQUE requête, sur un thread réseau
    override fun intercept(chain: Interceptor.Chain): Response {
        // 1. la requête d'origine, complétée du jeton s'il existe. Une
        //    requête OkHttp est immuable : newBuilder() en fabrique une
        //    copie modifiable.
        val jeton = auth.accessToken
        val requete = if (jeton == null) {
            chain.request()
        } else {
            chain.request().newBuilder()
                .header("Authorization", "Bearer $jeton")
                .build()
        }
        // 2. on laisse la requête poursuivre son chemin jusqu'au serveur
        val reponse = chain.proceed(requete)
        // 3. jeton refusé : on déconnecte l'utilisateur. Cette méthode
        //    s'exécute sur un thread réseau ; or seDeconnecter() modifie
        //    l'état affiché par l'interface : on confie donc cet appel au
        //    thread principal (post), sans attendre qu'il soit exécuté - le
        //    pendant du unawaited(auth.seDeconnecter()) de la version Flutter.
        if (reponse.code == 401) {
            threadPrincipal.post { auth.seDeconnecter() }
        }
        return reponse
    }
}

    Commentons ce code :

    • ligne 26 : la classe implémente l’interface [okhttp3.Interceptor]. OkHttp fait passer chaque requête par les intercepteurs du client avant de l’envoyer, et chaque réponse avant de la rendre à l’appelant : la notion d’intercepteur HTTP d’Angular. La version Flutter, faute d’un tel mécanisme dans le package [http], enveloppait le client HTTP dans une classe à elle ;
    • ligne 30 : un [Handler] associé au thread principal ([Looper.getMainLooper()]) : il permet de lui confier du travail depuis un autre thread ;
    • lignes 41-43 : une requête OkHttp est IMMUABLE : [newBuilder()] en fait une copie modifiable, complétée de l’entête [Authorization] ;

// -------------------------------------------------------------------------
// Portage de lib/core/i18n/translations_service.dart : le passage
// français/anglais de l'interface, à la volée, sans relancer
// l'application. Les dictionnaires sont les MÊMES fichiers JSON que ceux
// des clients Flutter et Vue.js de ce cours (fr.json, en.json), placés ici
// dans app/src/main/assets/i18n/ : le dossier assets/ d'un projet Android
// est embarqué tel quel dans l'application (le fichier .apk), comme les
// assets déclarés dans le pubspec.yaml de la version Flutter.
//
// Remarque : la méthode "officielle" d'Android pour traduire une
// application repose sur des fichiers de ressources res/values/strings.xml
// (français) et res/values-en/strings.xml (anglais), le système
// choisissant le bon fichier selon la langue du TÉLÉPHONE. Ce document
// garde les dictionnaires JSON communs à toutes les variantes du cours,
// et la bascule FR/EN dans l'application elle-même, comme le faisait
// l'application d'origine (2014).
// =========================================================================

package fr.rdvmedecins.client.core.i18n

import android.content.SharedPreferences
import android.content.res.AssetManager
import androidx.compose.runtime.getValue
import androidx.compose.runtime.mutableStateOf
import androidx.compose.runtime.setValue
import androidx.core.content.edit
import fr.rdvmedecins.client.core.models.JsonRdv
import kotlinx.serialization.json.JsonElement
import kotlinx.serialization.json.JsonObject
import kotlinx.serialization.json.JsonPrimitive
import kotlinx.serialization.json.jsonObject

class TranslationsService(
    private val assets: AssetManager,
    private val prefs: SharedPreferences,
) {
    // la langue affichée : un état Compose. Comme t(...) ci-dessous LIT
    // cette propriété, tout texte affiché avec t(...) est automatiquement
    // réaffiché quand la langue change - aucun context.watch<...>() à
    // écrire, contrairement à la version Flutter.
    var langueCourante by mutableStateOf(prefs.getString(CLE_LANGUE, null) ?: LANGUE_PAR_DEFAUT)
        private set

    // les dictionnaires déjà chargés, par langue ("fr" -> {...})
    private val dictionnaires = mutableMapOf<String, JsonObject>()

    fun changerLangue(langue: String) {
        if (langue == langueCourante) {
            return
        }
        dictionnaire(langue) // charge le dictionnaire AVANT de changer de langue
        langueCourante = langue
        prefs.edit { putString(CLE_LANGUE, langue) }
    }

    // -----------------------------------------------------------------------
    // t("LOGIN.TITLE") : parcourt le dictionnaire de la langue courante
    // segment par segment ("LOGIN", puis "TITLE"). Si la clé est
    // introuvable, on renvoie la clé elle-même : le texte manquant reste
    // ainsi visible à l'écran, sans faire planter l'application.
    // -----------------------------------------------------------------------
    fun t(cle: String): String {
        var valeurCourante: JsonElement = dictionnaire(langueCourante)
        for (segment in cle.split('.')) {
            valeurCourante = (valeurCourante as? JsonObject)?.get(segment) ?: return cle
        }
        val primitive = valeurCourante as? JsonPrimitive
        return if (primitive != null && primitive.isString) primitive.content else cle
    }

    // -----------------------------------------------------------------------
    // le dictionnaire d'une langue, chargé au premier besoin puis gardé en
    // mémoire. getOrPut : renvoie la valeur associée à la clé, ou exécute
    // le bloc, mémorise son résultat et le renvoie. La lecture est
    // synchrone : les deux fichiers ne font que quelques centaines
    // d'octets, leur lecture est instantanée.
    // -----------------------------------------------------------------------
    private fun dictionnaire(langue: String): JsonObject =
        dictionnaires.getOrPut(langue) {
            assets.open("i18n/$langue.json").bufferedReader().use { lecteur ->
                JsonRdv.parseToJsonElement(lecteur.readText()).jsonObject
            }
        }

    companion object {
        private const val CLE_LANGUE = "rdvmedecins.langue"
        private const val LANGUE_PAR_DEFAUT = "fr"
    }
}

    Commentons ce code :

    • lignes 43-44 : [langueCourante] - un état observable. Comme [t(...)] LIT cette propriété, toute fonction @Composable qui affiche un texte avec [t(...)] est recomposée automatiquement quand la langue change : aucun [context.watch<...>()] à écrire ;
    • lignes 49-55 : [changerLangue(...)] - charge le dictionnaire AVANT de changer de langue, puis mémorise le choix dans les préférences ;
    • lignes 64-70 : [t("LOGIN.TITLE")] - parcourt le dictionnaire segment par segment. [as?] est le transtypage « sûr » de Kotlin : il donne [null] (au lieu d’une exception) si l’objet n’est pas du type demandé ; combiné à [?: return cle], il fait renvoyer la clé elle-même dès qu’un segment est introuvable - le texte manquant reste visible à l’écran ;
    • lignes 80-83 : [dictionnaire(langue)] - [getOrPut] renvoie le dictionnaire déjà chargé, ou exécute le bloc (lecture de [assets/i18n/<langue>.json]), mémorise son résultat et le renvoie. La lecture est synchrone : les deux fichiers ne font que quelques centaines d’octets.

        expanded = ouvert,
        onExpandedChange = { ouvert = it },

    }

                    onSelection = { idClient = it },
                    modifier = Modifier.fillMaxWidth(),
                )
            }
        },
        // "Confirmer" : désactivé tant qu'aucun patient n'est choisi
        confirmButton = {
            Button(
                enabled = idClient != null,
                onClick = { idClient?.let(onConfirmer) },
            ) { Text(t("BOOKING_DIALOG.CONFIRM")) }
        },
        dismissButton = {
            TextButton(onClick = onFermer) { Text(t("BOOKING_DIALOG.CANCEL")) }
        },
    )
}

    Commentons ce code :

    • lignes 8-15 : le commentaire d’en-tête résume la différence structurelle avec la version Flutter. Flutter OUVRAIT la boîte de dialogue avec [showDialog(...)] et ATTENDAIT son résultat (un [Future<int?>]). En Compose, une boîte de dialogue est un élément d’affichage comme un autre : elle est affichée tant que la fonction qui l’appelle l’appelle. Elle ne « renvoie » rien : elle signale le choix par deux fonctions, [onConfirmer] et [onFermer] - exactement les deux événements [confirmer] / [fermer] du composant [BookingDialog.vue] de la variante Vue.js ;
    • ligne 48 : le patient choisi : [rememberSaveable], il survit à une rotation de l’écran pendant que la boîte de dialogue est ouverte ;
    • lignes 50-52 : [AlertDialog(...)] - la boîte de dialogue Material 3, avec un titre, un contenu ([text]) et deux boutons. [onDismissRequest] est appelée quand l’utilisateur touche en dehors de la boîte ou appuie sur la touche « retour » du téléphone ;
    • lignes 73-76 : le bouton « Confirmer », désactivé tant qu’aucun patient n’est choisi. [idClient?.let(onConfirmer)] : si [idClient] n’est pas [null], on appelle [onConfirmer] avec sa valeur.
